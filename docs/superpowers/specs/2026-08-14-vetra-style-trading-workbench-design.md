# Vetra 风格 A 股交易执行台设计

## 目标与范围

将前端重构为面向“人工实盘执行者”的明亮后台工作台。用户在华泰证券完成实际下单；本系统必须把本次交易的扫描、选股依据、执行计划、实际成交回填、持仓和复盘集中展示，并明确区分真实数据、等待数据和阻塞原因。

本设计只确定交易后台的产品与视觉规范，不接券商、不自动下单、不修改既有数据库或后端接口。

## 视觉方向

整体采用用户确认的 Vetra 风格：明亮柔和、白色侧边栏、圆角悬浮卡片、较大的留白、珊瑚色主操作与轻量内容密度。不得复制 Vetra 的品牌、源码、图标、插画、页面素材或具体交易内容。

| Token | 值 | 用途 |
|---|---:|---|
| 页面底色 | `#F8F7FF` | 主内容背景 |
| 表面 | `#FFFFFF` | 侧边栏、卡片、顶栏 |
| 正文 | `#312C46` | 标题、主要信息 |
| 次级文字 | `#9490A5` | 时间、数据状态、辅助说明 |
| 主强调色 | `#F1846D` | 启动交易、当前导航、关键待办 |
| 主强调浅色 | `#FFF0EC` | 当前导航与弱强调背景 |
| 成功/进行中 | `#6CCBA7` | 正常、已完成、可执行 |
| 提醒/观察 | `#F6BD4F` | 延迟、等待确认 |
| 风险/阻止 | `#D95F55` | 不可执行与风险事件 |

字体使用系统中文无衬线字族，数据列使用等宽数字。卡片圆角为 12–14px，轻阴影仅用于抬升信息层级；不使用深色终端、荧光绿或密集表格作为默认视觉。

页面唯一的“特色组件”是交易路径：用紧凑的四步状态列串联“启动交易 → 扫描与候选池 → 华泰成交回填 → 持仓与复盘”。它表达真实执行顺序，不作为装饰编号。

## 信息架构

侧边栏固定为以下用户可理解的项目：

```text
概览
当前交易
市场扫描
持仓与记录
交易规则
设置
```

不展示“交易实例”、“影子体系”、“任务锁”、“策略版本 ID”等后台实现词。策略版本和数据截面仅在计划详情的“数据与依据”展开区显示。

### 概览

顶部是本次交易状态和“启动本次交易”。主区域包括：

1. 本次交易概览：现金、总仓位、已实现/浮动盈亏、计划生成状态；未启动时只显示真实空状态。
2. 执行进度：待执行、部分成交、已成交、被阻止的数量和原因入口。
3. 今日操作摘要：最多展示当前真实计划；没有计划时解释“等待扫描”、“无符合标的”、“数据不足”或“风控阻止”。
4. 交易路径：用当前步骤和下一步动作说明用户应做什么。

### 当前交易

这是实际操作页。每个计划以一行或可展开卡片呈现，字段必须包括：

- 证券代码、名称、资产类型；
- 入选理由、信号时间、数据状态；
- 建仓/加仓/减仓/清仓动作、建议数量和目标仓位；
- 参考价、允许价格区间、失效条件、有效期；
- 华泰报价确认、实际成交价、数量、时间、费用与未成交原因；
- 当前成本、持仓、浮动盈亏与完整动作历史入口。

实际成交填写区只存在于该计划行，不另设“成交回填”页面。未确认报价不能保存；回填成功后，持仓和盈亏在同页更新。

### 市场扫描

展示可复现的选股证据：扫描范围（沪深主板，ETF 数据准备后才显示）、`as_of` 数据截面、最近扫描时间、候选池增减、每只候选标的入选和淘汰理由。数据尚未准备、过期或扫描失败时明确显示原因和恢复动作。

### 持仓与记录

以真实成交派生的持仓和动作历史为唯一数据来源。按证券展示数量、成本、最新价、浮动盈亏、最近动作；展开后显示建仓、加仓、减仓、清仓、成交费用及计划到成交偏差。无成交时显示真实空状态。

## 状态与文案规则

| 状态 | 展示内容 | 用户下一步 |
|---|---|---|
| 未启动 | 说明未生成计划的原因 | 点击“启动本次交易” |
| 计划生成中 | 当前阶段、开始时间、可见进度 | 等待或查看失败原因 |
| 无标的 | 扫描范围、筛选结果和无标的原因 | 等待下一窗口或结束交易 |
| 可执行 | 股票、理由、动作、区间和失效条件 | 在华泰确认报价后下单并回填 |
| 被阻止 | 明确风险码和缺失数据 | 修复数据或不执行 |
| 已成交/部分成交 | 实际成交、持仓、成本和偏差 | 继续完成剩余计划或复盘 |

界面不得用示例股票、示例价格、示例收益或伪造的实时状态填充真实交易页面。原型和演示页面必须有清晰“演示数据”标记。

## 后端契约影响

现有 `trade_run` API 是数据来源；实现前需补足或确认以下展示字段，不改变账务语义：

- 交易概览：运行状态、现金、仓位、真实/浮动盈亏、计划统计、当前生成步骤和失败信息；
- 计划：候选理由、策略可读说明、数据截面、价格区间、失效条件、报价确认状态、成交回填字段；
- 候选池：扫描范围、扫描时间、数据状态、候选/淘汰理由和更新时间；
- 持仓：动作时间线、计划关联、成交费用、成本、盈亏、最新可得行情状态；
- 审计与风险：面向执行者的中文原因和可执行恢复建议。

缺失字段先以显式空状态和“数据暂未提供”呈现，不能由前端推断或伪造。任何新增表、字段或索引必须通过新的不可变 SQL 迁移后同步到 VPS MySQL；本设计阶段不产生 SQL 变动。

## 实施顺序

1. 前端建立 Vetra 风格壳：色彩 token、侧边栏、顶栏、响应式卡片与路由。
2. 实现“当前交易”主页面和真实空/加载/失败状态，先接现有 `trade_run` 查询接口。
3. 补齐计划详情、报价确认与成交回填，使回填留在同一计划行。
4. 接入候选池、扫描进度、持仓动作历史与风险说明；缺失 API 再按契约扩展后端。
5. 用隔离测试数据验收数据状态、成交回填、持仓更新和所有空/错状态；随后由用户在 VPS 部署代码并进行人工验证。

## 验收标准

- 视觉上保持 Vetra 式明亮、柔和、圆角卡片和珊瑚色主操作，且没有复制其受保护资产。
- 用户可在一个“当前交易”页面内完成从看理由到回填成交的全过程。
- 每一只真实股票都有原因、动作、仓位、价格区间、成交、成本、盈亏和动作历史入口。
- 空状态、数据延迟、扫描失败、无标的和风控阻止均有真实、明确、可行动的说明。
- 不显示影子体系，也不以内部系统词汇代替用户任务。
- 页面在桌面端和窄屏下可用，表格必要时横向滚动但不截断关键状态。
